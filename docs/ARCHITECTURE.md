# IllumiNET Architecture

This document describes the planned shape of IllumiNET. It is forward looking
and will evolve alongside the implementation. Anything described here that
does not yet exist in code is marked as planned.

## Datasource

The first target platform is the Cisco Nexus 9000 family running NX-OS,
because that is the platform where the operational lessons from
`nexus_traffic_monitor` are sharpest. Arista EOS support is planned for the
second milestone (M2), and Juniper Junos for the third (M3). Each platform
introduces its own quirks around counter availability, clearing semantics, and
streaming cadence, and the adapter layer is the place those quirks are
contained.

## Transport

gNMI streaming telemetry is the primary transport. It is supported across all
three target vendors and is the cheapest path to high-resolution per-queue and
per-priority counters. Where gNMI does not expose a state that operators
actually need (typical examples include buffer pool occupancy on older NX-OS
trains, certain microburst counters, and clearing of specific counter groups),
the adapter falls back to the vendor-native management plane: NX-API for
Cisco, eAPI for Arista, and NETCONF for Juniper. The fallback is explicit and
opt-in per counter, not a wholesale alternative.

## Core

The core pipeline maintains a vendor-agnostic, normalized domain model
(`internal/core/model`) and is responsible for three jobs beyond plain
ingestion:

1. **Correlation.** Per-interface, per-queue, and per-buffer samples must be
   joined into a single coherent view of each port at each tick. Different
   counters often live behind different gNMI paths with different update
   cadences, and the pipeline reconciles them.
2. **Enrichment.** LLDP neighbor data is consumed to attach topology context
   to each sample. Neighbors are classified as host, switch, or other, and
   switch-facing ports are further split into Core and Edge in the operational
   sense established by `nexus_traffic_monitor`. This classification drives
   most useful dashboards and alerts.
3. **Dispatch.** Enriched samples are handed to one or more configured
   exporters.

## Output

OpenTelemetry OTLP over gRPC is the primary exporter. It is the format the
rest of the pipeline is designed around and the one that will receive new
features first. Prometheus remote write is supported for environments that
already standardize on Prometheus. InfluxDB Line Protocol on stdout is
supported as a compatibility output, so that operators currently running
`nexus_traffic_monitor` under Telegraf's `inputs.exec` plugin can swap
IllumiNET in without rebuilding the rest of their pipeline.

## Domain knowledge (RoCEv2 specific)

The features below are the reason this project exists rather than being a
thin wrapper over a generic gNMI-to-Telegraf config. Each one reflects a
lesson learned operating lossless fabrics.

- **PFC asymmetric monitoring.** PFC pause counters are most useful when the
  RX direction (pauses received on a port, that is, an egress signal from
  this switch toward the peer's ingress) and the TX direction (pauses
  generated by this switch, an ingress signal back to the peer) are tracked
  and visualized separately. Aggregating them hides the direction in which
  congestion actually originates.
- **ECN counters.** Per-queue ECN-marked packet counters are correlated with
  PFC and buffer state to distinguish soft signaling (ECN) from hard
  backpressure (PFC).
- **Burst peak-time timestamping.** Microbursts are recorded with the
  timestamp of the observed peak inside the sample interval, not just the
  interval boundary, so that burst events can be aligned across switches.
- **Buffer counter clearing conflicts.** Several platforms expose buffer
  occupancy counters whose semantics depend on whether and when they were
  last cleared. The collector tracks clearing events and refuses to compute
  deltas across a clear, rather than emitting silently wrong values.
- **Packet size distribution.** Per-interface packet size histograms are
  collected where the platform exposes them, because lossless workloads have
  characteristic size distributions whose drift is an early warning signal.

## Roadmap notes

- M1: NX-OS adapter (gNMI primary, NX-API fallback), OTLP exporter, LLDP
  enrichment with Core vs. Edge classification, PFC and ECN basics.
- M2: Arista EOS adapter planned. Buffer occupancy and microburst peak-time
  timestamping generalized across vendors.
- M3: Juniper Junos adapter planned. Prometheus remote write exporter
  hardened for production scale.
